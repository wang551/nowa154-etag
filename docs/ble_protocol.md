# BLE 传图协议

> 适用于本 fork（含 `0x05`/`0x06` 新命令）。`0x00`–`0x04` 与上游 ATC_TLSR_Paper
> 兼容；参考实现见 `web_tools/nowa152_image_upload.html`。

## 服务与特征

| 用途 | UUID |
|---|---|
| EPD 服务 | `13187b10-eba9-a3ba-044e-83d3217d9a38` |
| EPD 写特征（图像命令） | `4b646063-6264-f3a7-8941-e65356ea82fe` |
| RxTx 服务（上游，设时间等） | `0x1F10` |
| RxTx 写特征 | `0x1F1F`（`0xDD` + 6 字节时间 = 设时钟，上游功能） |

> UUID 手抄时注意第四段是 `9a38`（不是 `a38`）——回显的报错里是错的那个。

广播间隔 1 秒，扫描需要 10 秒以上才能发现设备。

## EPD 命令表（写入 EPD 特征，首字节为命令）

| 命令 | 载荷 | 功能 |
|---|---|---|
| `0x00` | `<fill>` | 清双平面：黑白缓冲填充 fill 字节（通常 `FF`=白）、红平面清零、复位平面选择与写指针，提速连接 |
| `0x01` | — | 把双平面推送到屏上刷新 |
| `0x02` | `<hi> <lo>` | 设置写指针 byte_pos（大端） |
| `0x03` | `<data…>` | 把 data 写入**当前选中平面**（见 `0x06`）的 byte_pos 处，写完指针前移 |
| `0x04` | — | 把 epd_buffer 按 TIFF G4 解码并显示（上游路径） |
| `0x05` | `<0/1>` | **新增**：1 = 锁定自定义图片（跳过每分钟时钟重画）；0 = 恢复并立即重画时钟。易失，重启回时钟 |
| `0x06` | `<0/1>` | **新增**：选择 `0x03` 的写入平面（0 = 黑白 `0x24` RAM，1 = 红 `0x26` RAM）并把写指针归零。旧固件收到走 default 忽略 → 红上传退化为无害空操作 |

## 像素打包公式（152×152，δ=8）

黑白平面（`0x24` RAM，0 = 黑，初始全 `FF`）——黑像素 `(x, y)`（玻璃坐标，x 左→右，y 上→下）：

```c
buf[(151 - x) * 20 + ((y + 8) >> 3)] &= ~(0x80 >> ((y + 8) & 7));  // 字节内 MSB-first
```

红平面（`0x26` RAM，1 = 红，初始全 `00`）——红像素置位而非清位：

```c
buf[(151 - x) * 20 + ((y + 8) >> 3)] |= (0x80 >> ((y + 8) & 7));
```

缓冲总长 `152 × 20 = 3040` 字节。

## 完整发送序列

```
05 01                 # 锁定（防止时钟覆盖）
00 FF                 # 清双平面
02 00 00              # 写指针归零
03 <240B> × 13        # 黑白平面数据（3040 = 13 × 240 - 80，最后一包短）
06 01                 # 切到红平面
03 <240B> × 13        # 红平面数据（无红像素可整段跳过）
01                    # 刷新
```

每包 240 字节数据 + 1 命令字节 = 241 ≤ MTU 247。

## 蓝牙 OTA（service `0x221F`，上游原版）

固件 OTA 管线（`ota.c` / `app_att.c`）fork 未改动，与上游完全一致。特征 `0x331F`
是**带响应写 + notify 同一特征**：先 `startNotifications()` 订阅再写。
收到首个 OTA 写包时固件自动把连接间隔切到 7.5ms（`ble.c` 的 `otaWritePre`）。
帧格式：`payload[0]` = 命令，后接 4 字节**大端**地址。

| 命令 | 载荷 | 功能 |
|---|---|---|
| `0x00` | — | 立即重启 |
| `0x01` | `<addr BE32>` | 擦 4KB 扇区（只接受 `0x20000`–`0x3FEFF`），notify 回显原帧 |
| `0x02` | `<addr BE32>` | 把 256B RAM 缓冲写到暂存区 addr 处，随后清缓冲 |
| `0x03` | `<data…>` | data 追加进 RAM 缓冲（超 256B 静默丢弃，会刷坏镜像） |
| `0x04` / `0x05` | `<addr>` | 回读 flash / RAM 缓冲 20 字节，notify 返回 |
| `0x06` | — | 对整个暂存区（`0x20000` 字节）求 16 位**字节和**，notify `[07 hi lo]` |
| `0x07` | `C0 01 CE ED <crc16>` | 魔数正确即落盘：擦 `0x00000`–`0x1FFFF`（运行固件）→ 拷贝暂存区 → 重启 |

> **`0x07` 的固件端 CRC 守卫是死代码**（上游 bug）：它比较的 `out_buffer[5]/[6]`
> 从未被任何命令写入、`crc_out` 又被传输命令清 0，等效于"只验魔数"——上游 OTA
> 页传完不发 `0x06` 直接发 `0x07`，暂存区哪怕损坏也会被刷成运行固件（刷坏的主因）。
> 更微妙的是：发过 `0x06` 后 `crc_out` = 真实校验和，`0x07` 反而会被静默拒绝落盘。

**安全刷写序列**（`web_tools/nowa152_image_upload.html` 的实现，两步确认）：

```
01 <addr> × 32                 # 整暂存区擦除（0x20000 + k×0x1000，k=0..31）
03 <240B> 03 <16B> 02 <addr>   # 每个 256B bank 一循环（末 bank 可短）；
                               #   241B 写，MTU 协商到 23 时自动降级 19B
06 → notify [07 hi lo]         # 设备端字节和，必须 == 本地值（bin 按 0xFF
                               #   补齐到 0x20000 后逐字节求和）才继续
03 00×20                       # 守卫复位①：crc_out 清 0、RAM 缓冲前 20B 归零
05 00 00 00 00 → notify 00×20  # 守卫复位②：out_buffer ← 20×0 并回读确认全零
（停下等用户确认）
07 C0 01 CE ED <hi lo>         # 落盘 + 重启；CRC 字节按协议带上，当前固件忽略
```

> 守卫复位两帧是对 `ota.c` 现状的**确定性利用**：把 `0x07` 守卫的两个比较量恢复
> 成通过值（`out_buffer[5]/[6]` = 0、`crc_out` = 0），既完成了真校验又能正常落盘。
> **若未来修改固件 `0x07` 守卫逻辑，这两帧必须与固件成对更新。**

安全设计：传输与校验只写暂存区，任何异常（写失败、断连、校验不一致、中止）
都不发 `0x07`，运行固件不受影响；只有设备端字节和与本地一致才解锁「确认刷入」，
且传输期间与其余 BLE 功能完全互斥（杜绝两次传输交错写坏暂存区）。

> **风险**：`0x07` 落盘的数秒内设备关中断擦写自身，此时断电 / 断连没有
> bootloader 可回滚，只能 UART 重刷（见 README「刷机」节）。

## Windows / Web Bluetooth 排坑

- GATT 发现偶发失败：用 `getPrimaryService(uuid)` **单服务直查**，
  `getPrimaryServices()` 全量枚举更容易踩缓存空表
- 连接/发现要带**重试 + 手动重连按钮**（上游网页工具静默重试 ≤6 次掩盖过此问题）
- 断开连接后标签恢复广播约需 1 个广播间隔（本 fork 已修复上游"断连后永不广播"
  的 bug；旧固件表现为断连一次后从扫描中消失，只能抠电池）
- `file://` 协议下部分浏览器拦截 Web Bluetooth：`python -m http.server` 走 localhost
